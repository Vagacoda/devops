# 방명록 GitOps 프로젝트 발표 대본 (약 3분)

## 1장 — 결과 (약 30초)

발표 시작하겠습니다. 기존 방명록 앱을 Docker Compose로 실행한 뒤, Minikube와 Argo CD로 배포했습니다. 제목과 색상, web 개수와 포트를 바꿨고, 코드 문구도 `GitOps 배포`로 수정했습니다. GitHub Actions가 만든 새 이미지 `1effe2d`를 배포 파일에 지정하자 Argo CD가 자동으로 반영했습니다. 오른쪽은 정상 동기화 상태이고, 왼쪽은 최종 화면입니다.

## 2장 — Redis 연결 실패 (약 50초)

처음 Argo CD를 연결했을 때 설정은 `Synced`였지만 건강 상태는 `Degraded`였습니다. Pod를 확인하니 web 네 개 중 하나가 `0/1`이었습니다. Pod 이벤트에는 `/readyz` 검사 실패와 503이 있었고, 로그에는 Redis 연결이 거부되어 메모리 모드로 시작했다는 메시지가 있었습니다. Redis가 실행 중인 것을 확인한 다음 문제 Pod만 다시 생성했습니다. 새 Pod가 Redis에 연결하면서 네 개 모두 준비 완료가 되었고 Argo CD도 `Healthy`로 바뀌었습니다. 이때 프로세스가 `Running`이어도 실제 요청을 받을 준비가 끝난 것은 아니라는 점을 알았습니다.

## 3장 — Probe 경로 오류와 복구 (약 60초)

두 번째는 오류를 직접 재현했습니다. 배포 파일의 준비 상태 검사 경로를 `/readyz`에서 존재하지 않는 `/readyz-broken`으로 바꿔 PR을 합쳤습니다. Argo CD는 Git의 설정을 동기화했지만, 새 Pod는 `0/1`이었고 이벤트에 HTTP 404가 남았습니다. 즉 이미지나 컨테이너 실행 자체보다 검사 주소가 문제였습니다. 다시 `/readyz`로 고친 PR을 합치자 새 배포가 완료됐습니다. 최종적으로 web 세 개가 모두 `1/1`이고 Argo CD가 `Synced`, `Healthy`인 것을 확인했습니다. 오류를 볼 때는 Pod 상태만 보지 않고 `describe`의 이벤트를 확인하는 것이 빨랐습니다.

## 4장 — 배운 점 (약 35초)

코드를 바꾸고 GitHub Actions에서 이미지가 만들어져도 화면은 곧바로 바뀌지 않았습니다. Kubernetes 배포 파일이 여전히 예전 이미지 태그를 가리켰기 때문입니다. 새 태그를 Git에서 바꾼 뒤에야 Argo CD가 새 버전을 배포했습니다. 다음에 다시 한다면 빌드 성공, 배포 파일의 태그, Argo CD 동기화, Pod 준비 상태, 브라우저 화면 순서로 확인하겠습니다. 감사합니다.
